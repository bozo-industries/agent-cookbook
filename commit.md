# Commit, Push, and Deploy Workflow

For every task that changes a Git worktree:

1. Work in small, coherent checkpoints. Each commit should have one reviewable purpose; do not bundle several independent features, fixes, refactors, or documentation changes into one bulk commit.
2. At each checkpoint, run the tests and checks appropriate to that change. Commit only after they pass, or clearly report any known failure or blocker.
   - Distinguish direct dependency discovery from complete released-tree coverage. Inspect tracked overrides/resolutions and installed transitive inventories; a clean top-level outdated result does not establish that every pinned package is current. Preserve upstream dependency constraints unless a separately reviewed override is justified.
   - Validate nested tool workspaces with their own declared dependencies and a clean parent directory. A root `node_modules` can supply undeclared type packages and conceal a standalone CI failure. Include required generated inputs, keep build output out of source type checking, and install at the final validation path before testing the isolated workspace.
   - If a high-core workstation test run times out under worker contention, preserve the failing timings and rerun with a bounded worker pool before changing deadlines, assertions, or source. Record that execution limit and still run the repository's exact canonical CI on its intended platform before production promotion.
3. Review the staged diff. Include only work in scope, and never commit unrelated user changes, generated noise, captures, credentials, or secrets.
   - When selective staging produces a source snapshot different from the tested worktree, export the exact index into a fresh temporary directory and run the relevant build/tests there too. A dirty worktree can supply missing methods, visibility changes, or request parameters that conceal a broken staged commit. Resolve required dependencies explicitly without absorbing unrelated prototype changes, and distinguish staged-snapshot results from worktree/device results in the handoff.
   - GitHub source tarballs and `git archive` can omit tracked files through `.gitattributes` `export-ignore` or alter them through `export-subst`. Before treating an archive as the exact source commit, reconcile its contents against that commit's Git tree and blob hashes, including workflow, build-context and contribution files. Preserve executable and symlink semantics on the intended platform; a Windows pointer-file checkout does not verify a Linux packaging symlink.
4. Follow the repository's commit-message rules. When no stricter local rule exists, begin the imperative subject with `[feat]`, `[fix]`, `[perf]`, `[refactor]`, `[docs]`, `[test]`, `[build]`, `[ci]`, `[chore]`, or `[revert]`.
5. In PowerShell, do not embed `\n` escape text inside a quoted `git commit -m` argument; PowerShell passes it literally. Supply each paragraph with a separate `-m` argument, or use a UTF-8 message file with `git commit -F`, so the recorded message contains real line breaks.
6. When repository policy permits intentionally skipping CI, put `[skip ci]` immediately after the normal tag, for example: `[docs][skip ci] Clarify deployment steps`. Never append it at the end.
   - Repository exception: never use `[skip ci]` in `bozo-industries/agent-cookbook`; use only the normal commit-type tag.
7. Push every completed, tested checkpoint to its configured remote. Do not leave finished work only in the local worktree unless pushing is technically blocked or a higher-priority instruction forbids it; report the exact blocker.
   - Before publication, verify the recorded author and committer against the repository's authorized attribution and check any required signature. A configured identity or a valid signature alone does not prove those metadata fields are correct. Repository-local user settings can override global defaults; use an explicit per-command identity when policy requires it without changing unrelated global settings.
8. Deploy only after the tested commit has been pushed. If deployment is requested or is an established required step, deploy and verify it. If deployment intent is uncertain, ask before deploying. That uncertainty does not block committing and pushing.
9. Report the commit hash, pushed branch and remote, tests run, and deployment status. Never claim deployment based only on a local test or successful push.
10. In an allowlisted repository, verify that a new portable guide or asset is included by the intended ignore rules before staging references to it. A failed multi-path `git add` can still leave some requested paths staged; stop the checkpoint on that failure and inspect the exact index. Confirm every newly referenced file is present in the staged snapshot before committing and publishing the reference. Add only the specific portable path to the allowlist; never broadly unignore runtime or machine-local state.
