# pfSense and Proxmox Gateway Work

Use this guide when restoring or configuring pfSense under Proxmox, especially before moving existing guests behind it.

1. Restore an old gateway with both NICs disconnected and automatic startup disabled. Inspect its saved interfaces, DHCP services, NAT and firewall rules before connecting either NIC. A retained DHCP pool or default LAN allow rule can affect guests as soon as the inside link becomes active.
2. Prefer a verified management transport before configuring production routing. A running guest-agent process does not prove that Proxmox can execute commands through it. Test a harmless command. If local serial replies are unreliable, use a host-only management link with a bridge-port guard that blocks all guest forwarding. Keep the outside NIC disconnected until restrictive firewall rules are loaded.
3. When typing through QMP, send explicit key-down and key-up events and release modifiers before typing. Timed `send-key` calls can overlap and corrupt mixed-case input or Base64. Verify a short literal first, then verify the decoded artifact. Do not repeat a bootstrap solely because its final probe failed; inspect the actual process and source first.
4. Keep a temporary SSH authorized-key file under a protected directory owned by the intended account. A correctly hashed key under a writable ancestor such as `/tmp` can still fail OpenSSH `StrictModes`. Preserve existing access and pin the server key through the independently controlled VM path.
5. Follow the installed native reload script's PHP includes. For example, inspect `/etc/rc.filter_configure_sync` before calling `filter_configure_sync()`; its shaper and VPN dependencies may be required even when those features are unused. Inspect the installed configuration key before changing an option: the automatic administration rule is controlled by `system/webgui/noantilockout` in CE 2.7.0.
   Recheck configuration APIs after a version upgrade. CE 2.9.0 loads the configuration through `config.inc` and uses `config_get_path()` and `config_set_path()`; the older `parse_config()` function may be absent. Use the installed native script as the reference rather than carrying an old helper call across versions.
6. Treat parsed XML types carefully. Empty configuration sections can be strings rather than arrays. Check types before indexing them. To modify nested sections, address the original array by key; a reference loop over a null-coalescing expression can modify a temporary copy and retain the saved setting.
   Native PHP includes share global variables such as `$g` and `$config`. Use distinctive names for operation variables and loop items; assigning a gateway tuple to `$g` can overwrite pfSense's path settings and make an otherwise valid configuration appear unrecoverable. After a missing completion frame, check the saved XML and native configuration read before retrying a write.
7. Verify both saved configuration and active behavior after applying a stage. Confirm the DHCP daemon is stopped, the actual loaded rules contain the intended management allowance, broad administration rules are absent, and the same management command still succeeds. Keep bridge isolation in place until the stage passes.
   Use a usable host address for inside management. An old Linux bridge can have a subnet's network address configured while a newer gateway stack cannot communicate with it. Stage and verify a valid address without reloading the bridges; preserve external management, check for existing listeners and connections on the old address, and bind the management probe to the intended source. When removing a Linux primary address, account for secondary-address removal: temporarily enable `promote_secondaries` on that interface, verify the surviving address, and restore the prior setting.
8. Identify executable types before reading tool source as text. Some pfSense utilities are ELF binaries. Use their help or official documentation; do not feed binary contents into a UTF-8 JSON response. Read snapshot lists through the Proxmox API when a CLI subcommand does not support JSON output.
9. A package update check that reports repository errors followed by “up to date” has not established the installed version is current, even if it exits zero. Capture the package client's actual repository diagnostic. For the documented old-client certificate-chain failure, use Netgate's `certctl rehash` procedure, then verify the check with certificate and package-signature validation intact.
10. Save a recovery snapshot before upgrading. Run long updates as bounded jobs with separate submission and result records; expect a successful upgrade to reboot. Reconcile the actual version and saved job state before retrying. Migrate production guests only after the gateway upgrade, isolation and recovery checks pass.
11. Verify DHCP options in an actual client's addresses and routes after a fresh lease. A generated server configuration containing an option does not prove the server sends it or the client applies it. For isolated guests sharing one subnet, test both request and response paths through the firewall: a permitted request can still fail when the peer attempts a blocked direct return. Keep bridge isolation enforced independently of client routes, and prove permitted dependencies and denied direct traffic with real disposable peers before migration.

12. Reconcile retained DHCP leases when replacing or moving a reservation. Kea can retain a deleted guest's lease and give its replacement a pool address despite the new static reservation. Use the native control socket to delete only retired or mismatched leases, then verify their absence before permitting the new identity. Read raw control responses for lease ownership: the web UI helper can deduplicate actual leases against configured reservations and hide a stale hardware address. Do not edit the live lease CSV.
13. Polling alone does not protect a reused guest port name. Bind bridge permissions to the current kernel interface index as well as MAC and IP, so a recreated port cannot use the prior guest's rules before reconciliation. Test a recreated guest forging the old MAC/IP before enrollment, with a valid positive afterward. Newly created guests can appear with an unknown status in the cached cluster resource list; read their exact status endpoint before treating inventory as complete or approving a stopped fleet.
14. An Ethernet destination-MAC restriction for IP traffic must allow broadcast ARP requests for the gateway's owned addresses. Do not prepend a unicast-only MAC match to that ARP allowance. Verify that a fresh outside client learns the gateway's MAC and completes a routed TCP exchange without a manually installed neighbor; an existing ARP cache can hide a broken broadcast rule.
15. Serialize production network cutovers with the active fleet backup job, not only the target's current lock. A backup can advance to that guest after preflight and reject either management verification or rollback. Preserve the existing backup job, defer the cutover until it finishes, and recheck the target immediately before moving its NIC. After rollback, read the actual NIC configuration and guest address independently; any rejected restore command or mismatched state leaves recovery pending. Do not mark a rollback complete or cancel its recovery path merely because later commands succeeded.

16. Treat a custom DHCP script as a complete executable boundary. Use verified absolute utility paths because dhclient supplies a minimal environment, and authorize only the exact root-owned helper in the existing AppArmor local include. Validate and reload the native profile without disabling confinement globally. Retain each sanitized hook failure before a later lease overwrites its diagnostic. After removing an interface, reconcile ifupdown state; a stale configured entry can make a retry skip DHCP. Prove a fresh server ACK, applied address and routes, rather than treating a manually supplied lease as DHCP evidence.
17. A newly assigned IPv6 address can remain tentative while duplicate-address detection runs. A route that explicitly selects it as its preferred source can fail even though address installation succeeded. Prefer normal interface source selection, or wait for the address to become usable before selecting it explicitly; verify the final route and actual traffic.
18. Renew a link through its installed network manager. ConnMan can retain a DHCP lease across disconnect/connect and a virtual bridge move. Clear the selected service's IPv4 configuration, restore DHCP, and wait for the actual expected address before proceeding. During rollback, remove only the owned migrated addresses and routes, restore the original native configuration, and independently verify the original address and service behavior before stopping recovery.
